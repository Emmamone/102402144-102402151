# 校园失物招领 · 开发计划

## 1. 计划概览

**目标**：在保持 5 个页面外观与操作流程不变的前提下，完成前后端分离改造。

**基线**：现行源码是 5 个静态页面 + 一套定稿的「校园档案」视觉主题（墨绿 / 暖纸白 / 朱砂橙），主题目前以字节相同的内联 `<style>` 块复制在 5 个文件里。"外观不变"以**这一版**为基线，主题只会从 5 份副本收敛为 1 份共用文件，渲染结果不变。

**关联文档**：《产品需求文档》`docs/PRD.md`、《系统设计文档》`docs/system-design.md`、《代码规范》`docs/coding-standards.md`

**总工期**：约 5.5 人日（不含已完成的文档阶段）

**排序原则**（本计划的核心思路）：

1. **先机械重构，再改行为** —— 目录调整、文件改名、脚本拆分这些"不改行为"的动作集中放在第一阶段做完，这样后续每次改动都只动 `.js` 文件，出问题时责任边界清晰。
2. **先后端后前端，先读后写** —— 先把接口做出来，再把页面接上去；读路径（列表/详情/搜索）风险低、肉眼即可验收，先做；写路径（发布/标记已解决）涉及数据变更，后做。
3. **每个阶段结束时站点都必须是可运行、可验收的** —— 不允许出现"改到一半打不开"的中间状态。第五阶段结束时也只是一个功能完全可用的站点，不存在大爆炸式集成。
4. **每个阶段独立验收** —— 每个阶段都有明确的验收清单，验收不通过不进入下一阶段。
5. **测试与文档随代码同步产出** —— 每个阶段的任务清单里都包含"写测试"与"同步文档"两项；测试放在仓库根目录的**测试层** `tests/`（`unit` / `integration` / `contract` 三层），不散落在 `backend/` 里；每个阶段的验收都包含一条 `python -m pytest -q` 全绿，并**由 CI 在每次 push / PR 时自动复核**。细则见《代码规范》`docs/coding-standards.md`。

## 2. 阶段总览与依赖关系

```
阶段 0  机械重构（不改行为）
    │   目录调整 · 首页改名 · 主题样式抽取 · 脚本拆分
    ▼
阶段 1  数据层
    │   建表 DDL · 演示数据种子（幂等）
    ▼
阶段 2  读接口
    │   首页列表 · 搜索 · 详情   （此时后端可用 Python 接口文档单独验证）
    ▼
阶段 3  前端读路径改造  ◄── 站点在此阶段恢复"首页/搜索/详情完全可用"（只读）
    │   请求封装 · 共用工具 · 三个页面的 js 改造
    ▼
阶段 4  写接口 + 写路径改造  ◄── 站点在此阶段功能完整
    │   发布 · 标记已解决 · 发布页与成功页改造
    ▼
阶段 5  收尾与全量回归
        兼容路由 · README · 清理残留 · 端到端验收
```

**关键路径**：阶段 1 → 阶段 2 → 阶段 3 → 阶段 4。阶段 0 与阶段 5 是两端的一次性工作，不是瓶颈。

| 阶段 | 内容 | 预估 | 依赖 | 阶段末状态 |
| --- | --- | --- | --- | --- |
| 0 | 机械重构 | 0.75 人日 | 无 | 站点功能与外观与改造前完全一致，主题只剩一份 |
| 1 | 数据层 | 0.5 人日 | 阶段 0 | 数据库可建表、可重复播种 |
| 2 | 读接口 | 1 人日 | 阶段 1 | 3 个读接口可通过接口文档验证 |
| 3 | 前端读路径改造 | 1.5 人日 | 阶段 2 | 首页/搜索/详情由后端驱动，视觉不变 |
| 4 | 写接口 + 写路径改造 | 1 人日 | 阶段 3 | 发布与标记已解决可用，功能完整 |
| 5 | 收尾与回归 | 0.5 人日 | 阶段 4 | 全部验收项通过 |
