# 校园失物招领 · 代码规范

## 1. 适用范围与三条硬性约定

本规范适用于本项目的全部代码：`frontend/`、`backend/`、`tests/`。

**三条硬性约定**（不是建议，是"完成"的必要条件）：

| # | 约定 | 违反的判定 |
| --- | --- | --- |
| 1 | **写代码的同时写测试**：每实现一个函数或一个接口，同一次提交内必须带上对应的单元测试或集成测试。不允许"先写代码，测试回头补"。 | 提交里新增/修改了 `backend/` 下的代码，但 `tests/` 没有对应变更 |
| 2 | **测试写在测试层**：所有测试放在仓库根目录的 `tests/` 下，按 `unit/`、`integration/`、`contract/` 分层。不允许把测试文件散落在 `backend/` 里，也不允许在源码里写 `if __name__ == "__main__"` 式的临时验证脚本当作测试。 | 在 `backend/` 下出现 `test_*.py`，或存在靠手工点页面才能验证的逻辑却没有自动化测试 |
| 3 | **同步写文档**：代码变更若影响接口、需求、目录结构或开发顺序，必须在**同一次提交**里更新对应文档（见第 7 节）。 | 接口字段改了但 `docs/system-design.md` 的接口表还是旧的 |

> 说明：这三条与"保持页面不变"的约束并不冲突——页面不变指的是**渲染结果**，而渲染逻辑、数据来源、代码组织都在变，这些恰恰是最需要测试兜住的部分。

## 2. 分层与目录规范

```
campus-lost-found/
├── frontend/          展示层：5 个独立页面 + 单份主题 + 每页一个 js
│   ├── css/visual-theme.css
│   └── js/{api,common,index,search,detail,publish,success}.js
├── backend/           服务层：FastAPI 应用、数据访问、序列化、种子
│   ├── main.py        路由与装配
│   ├── db.py          连接与建表
│   ├── schemas.py     请求校验模型
│   ├── serialize.py   纯转换函数
│   └── seed.py        演示数据播种
├── tests/             测试层：unit / integration / contract
│   ├── conftest.py
│   ├── unit/
│   ├── integration/
│   └── contract/
├── docs/              文档层
└── db.sqlite3         运行时生成（不入库）
```

**分层原则**：

- **展示层不含业务逻辑**。前端只做三件事：发请求、把响应写进 DOM、给出与现状一致的交互反馈。任何"筛选、搜索、排序、状态判断、脱敏、编号生成"都必须待在服务层。
- **服务层按职责分文件，不按功能分**。`main.py` 只做路由声明与装配，不写 SQL；`db.py` 不写业务规则；`serialize.py` 只做数据转换且**全部是纯函数**（这是最容易也最该被单测覆盖的一层）。
- **测试层不得被生产代码导入**。测试可以导入 `backend`，反过来不行。
- **文档层与代码同仓**，随代码一起变更。

## 3. 测试规范

### 3.1 测试层结构

```
tests/
├── conftest.py                    公共 fixture：临时数据库、TestClient、演示数据
├── unit/
│   ├── test_serialize.py          脱敏、相对时间推导、编号生成、搜索索引拼装、类型/状态映射
│   └── test_schemas.py            请求模型校验（非法类型、空字段、时间格式）
├── integration/
│   ├── test_seed.py               建表与播种（幂等 / 演示数据一致 / 不覆盖用户数据 / 不碰 db.sqlite3）
│   ├── test_items_read.py         首页列表、搜索、详情（排序 / 条数 / 类型筛选 / 同义词命中 / 404）
│   └── test_items_write.py        发布（字段补全 / 编号 / 索引）、标记已解决（幂等 / 404 / 持久化）
└── contract/
    └── test_api_contract.py       接口返回字段与前端卡片模板的期望一致
```

### 3.2 单元测试（`tests/unit/`）

**写什么**：`backend/serialize.py` 与 `backend/schemas.py` 里的纯函数与校验规则。

**硬性要求**：

- **不得依赖数据库、网络、文件系统、当前时间**。凡涉及"当前时间"的函数，把时间作为参数传入（如 `format_relative(happened_at, now)`），不要在函数内部调 `datetime.now()`——否则测试不可重复。
- **一个测试只验一件事**，测试名说清"什么条件 → 什么结果"，例如 `test_mask_contact_11位手机号只露前三后四`、`test_time_display_为_None_时由_happened_at_推导`。
- **必须覆盖边界**：空值、`None`、长度临界（恰好 4 位 / 5 位）、类型非法值、时间跨天（今天 / 昨天 / 更早）。
- **必须覆盖保真规则**，这几条是数据层的核心决策，漏了就等于没有防线：
  - 演示数据的 `masked` **不能**由 `contact` 推导（`微信：zhang_cc2024` → `138****6621` 是写死的），断言时要用真实的那两条数据。
  - `card_desc` 与 `desc` 是**两段不同的文字**，不能用其中一个生成另一个。
  - `time_display` 非空时**必须原样返回**，不得被 `happened_at` 覆盖。

### 3.3 集成测试（`tests/integration/`）

**写什么**：5 个接口的端到端行为，通过 FastAPI 的 `TestClient` 发起真实 HTTP 请求。

**硬性要求**：

- **必须使用临时数据库**：fixture 为每个测试创建独立的 SQLite 文件（`tmp_path`），测试结束后销毁。**绝不允许连到仓库里的 `db.sqlite3`**——否则跑一次测试就污染了演示数据。
- **每个测试自己准备数据**：不依赖"另一个测试先跑过"。测试之间不得有顺序依赖。
- **接口测试必须断言到字段级**，不能只断言状态码 200。至少包含：
  - 首页列表：默认 6 条且顺序为 1–6；`type=seek` 为 3 条；`type=find` 为 3 条；`count` 与 `items` 长度一致。
  - 搜索：空关键词 8 条且顺序为 `1,7,5,3,2,4,6,8`；`校园卡` → 2 条；同义词命中（`蓝色卡套` → 1 号、`3号楼` → 4 号）；关键词 + 类型组合筛选。
  - 详情：`LF-001` 编号、绝对时间、`masked` 与 `contact` 同时返回且二者不同源；`id=4` 为已解决；`id=999` → 404 且错误体格式正确。
  - 发布：201 返回新 id 与编号；**后端补全的字段**（状态、图标、发布者、头像、脱敏串、搜索索引、`time_display` 为 `NULL`）逐项断言；发布后该记录能在首页与搜索里查到且排在首位。
  - 标记已解决：200 且状态变为已解决；**重复调用幂等**；对不存在的 id 返回 404；调用后重新查询状态已持久化。
- **必须覆盖路由顺序这条坑**：直接断言 `/api/items/home` 与 `/api/items/search` 返回 200（而不是被 `/{id}` 捕获后返回 422）。
- **幂等性要有测试**：连续执行两次播种，断言记录数不变、id 1–8 的字段不变、id ≥ 9 的用户数据不被覆盖。

### 3.4 契约测试（`tests/contract/`）

前端没有构建工具、也没有 Node 测试环境（已决策不引入），业务逻辑又全部下沉到了后端，所以**前端的正确性靠"契约"兜住**：

- 在 `tests/contract/test_api_contract.py` 里，集中声明**前端渲染所需的字段清单**——即 `js/common.js` 中 `renderCard` 与 `js/detail.js` 的 `render` 实际读取的每一个字段，以及首页/搜索/详情各自的 DOM 所需的字段。
- 对每个接口的返回体断言：**这些字段一个都不能少，且类型正确**（时间与描述是字符串、id 是整数、`status`/`type` 取值在枚举内）。
- 前端若新增了对某字段的依赖，必须同步在这个文件里加断言。
- 另有一个 `tests/contract/test_frontend_wiring.py`，对**前端源码文本**做静态检查，同样不需要浏览器或 Node：页面里不得再有内联样式/脚本、引用的本地资源必须真实存在、脚本引用顺序正确、已改造的页面不得再内嵌数据或依赖 `localStorage`。它还维护两张迁移进度表（`WIRED`、`LOCAL_STORAGE_ALLOWED`）——**页面完成改造后要同步改这两张表**，改漏了测试会失败。

**为什么值得单独一层**：前端是"改一个字没测试跑得起来但页面就白屏"的一层。字段名从 `desc` 改成 `cardDesc` 这类改动在后端测试里可能全绿，但页面会静默丢内容；契约测试就是这道防线。

### 3.5 测试数据规范

- 演示数据只在一个地方定义：`backend/seed.py`。**测试不得复制粘贴这 8 条数据**，必须通过调用 `seed` 或共享 fixture 获得，避免两份数据各自漂移。
- 断言里出现的字面量（如 `138****6621`、`今天 08:20`、`蓝色卡套`)必须与 `seed.py` 中的值一致；这条由 3.2 提到的"保真规则"测试反向保护。
- 测试可以造自己的数据（例如专门的边界数据），但必须用明显的命名（如 `_make_item(...)` 辅助函数）与演示数据区分开。

### 3.6 运行方式

```bash
pip install -r requirements-dev.txt     # pytest、httpx、ruff
python -m pytest -q                     # 全部
python -m pytest tests/unit -q          # 只跑单元测试（秒级）
python -m pytest tests/integration -q   # 只跑集成测试
ruff check .                            # 代码风格检查（只检查，不自动修改）
```

用 `python -m pytest` 而不是裸 `pytest`：前者会把当前工作目录加入 `sys.path`，测试才能 `import backend`，不需要额外配置 `pythonpath`。

依赖文件分工：

- `requirements.txt`：运行期依赖（`fastapi`、`uvicorn`）。
- `requirements-dev.txt`：开发与测试依赖（`pytest`、`httpx`、`ruff`），并**引用**运行期依赖。

### 3.7 完成的定义（DoD）

一个任务算"完成"，必须同时满足：

1. 功能实现，且手工验收项通过。
2. **对应的自动化测试已写并通过**（纯逻辑 → 单元测试；接口 → 集成测试；前端依赖的字段 → 契约测试）。
3. `python -m pytest -q` 与 `ruff check .` 本地全绿。
4. **CI 全绿**（见 3.8）——本地绿不替代 CI 绿。
5. 受影响的文档已在同一次提交里更新。
6. 页面外观与交互没有未经说明的变化。

### 3.8 持续集成

工作流文件：`.github/workflows/ci.yml`。

| 项 | 配置 |
| --- | --- |
| 触发 | 任何分支的 push、任何 PR，以及手动运行（`workflow_dispatch`） |
| 运行环境 | `ubuntu-latest` + Python 3.14 |
| 依赖安装 | `pip install -r requirements-dev.txt` |
| 执行顺序 | ① 确认前置条件（测试层目录 + 依赖文件）→ ② 准备 Python → ③ 安装依赖 → ④ `ruff check .` → ⑤ `tests/unit` → ⑥ `tests/integration` → ⑦ `tests/contract` |
| 超时 | 10 分钟 |

**规则**：

- 三个测试层各有独立的步骤，**哪一层挂了在 CI 页面上直接可见**，不需要翻日志找是哪类测试失败。
- **"目录存在但一个测试都没有"也算失败**：`pytest` 在什么都没收集到时返回**退出码 5**（官方文档："Exit code 5: No tests were collected"），是非零，步骤判失败。因此空层不会悄悄变绿——这条是上游依赖，不要试图用 `continue-on-error` 或容忍退出码 5 绕过。
- 由此带来一个**分阶段的必然结果**：测试是分层建设的（单元层先有、集成层次之、契约层最后），所以在三层都写出真实测试之前，CI 会一直红，且红的原因是"某一层还没有测试"。**这是正确信号，不是配置问题**；不要为了让早期阶段看起来是绿的而放宽守卫。转绿节点见《开发计划》。
- 前置条件检查**排在装依赖之前**，缺 `tests/unit`、`tests/integration`、`tests/contract`、`requirements.txt` 或 `requirements-dev.txt` 中任何一项时，第一步就以明确的错误信息失败——而不是让 pip 抛 `Could not open requirements file`、或让 `pytest` 抛 `file or directory not found` 这类看不出所以然的错。这是有意的：**没有测试就应当是红的**，不允许出现"没有测试却显示通过"的假绿。
- 失败顺序按测试金字塔从快到慢排列，风格问题与单元测试会最先暴露，不用等集成测试跑完。
- CI 红着不算完成；修复后重新推送即可重新触发。

> 前端遗留物扫描（内联样式与脚本、`localStorage` 残留、迁移进度一致性）**已固化进测试层**，见 `tests/contract/test_frontend_wiring.py`：它只读源码文本，不需要浏览器或 Node，因此与其他两层一样随 CI 运行，不必再靠阶段 5 的人工 grep。`insertLocalPost` 这类"某个旧函数必须消失"的检查，在对应页面迁移时一并加进去。

## 4. 后端代码规范（Python）

### 4.1 分层职责

| 文件 | 只负责 | 不得出现 |
| --- | --- | --- |
| `main.py` | 路由声明、依赖装配、静态挂载 | SQL 语句、数据转换逻辑 |
| `db.py` | 连接管理、建表 DDL、`init_db()` | 业务规则、序列化 |
| `schemas.py` | 请求/响应模型的字段与校验 | 数据库访问 |
| `serialize.py` | 行 → 响应对象的转换（**纯函数**） | 数据库访问、`datetime.now()` |
| `seed.py` | 幂等写入演示数据 | 被运行期代码导入 |

### 4.2 编码约定

- 遵循 PEP 8；`snake_case` 命名函数与变量，`PascalCase` 命名模型类。
- PEP 8 由 `ruff` 落地检查（配置见仓库根目录 `ruff.toml`，规则集 `E`/`F`/`W`/`I`，行宽 100）。提交前执行 `ruff check .`，CI 也会跑同一条命令；**不要**在 CI 之外依赖编辑器自动格式化，以免格式在不同机器上漂移。
- **公开函数写类型注解**（参数与返回值）。
- **时间只在一个地方取**：`serialize.py` 里的时间相关函数接受 `now` 参数；只有路由层或 `seed.py` 允许调 `datetime.now()` 并把它传下去。这是让单元测试可重复的前提。
- **不吞异常**。`try/except` 必须要么记录、要么转换后重新抛出；不允许 `except: pass`。
- **错误响应格式统一**：`{"code": "...", "message": "中文说明"}`；字段校验失败交给 Pydantic 的原生 422。
- **路由顺序**：`/api/items/home`、`/api/items/search` 这类字面量路径必须声明在 `/api/items/{id}` 之前，静态挂载放最后。改动路由时同步检查这一条。
- **SQL 用参数化占位符**（`?`），不做字符串拼接。
- 每个请求使用独立数据库连接，启用 `PRAGMA journal_mode=WAL`；不共享全局连接对象。

## 5. 前端代码规范（HTML / CSS / JS）

### 5.1 文件组织

- 一个页面一个 `.html`，**不做单页应用**，不合并页面。
- 一个页面一个同名 js（`index.js` / `search.js` / `detail.js` / `publish.js` / `success.js`）。
- 主题样式只有 `css/visual-theme.css` **一份**，各页用 `<link>` 引用。
- HTML 中**不得出现**内联 `<style>` 主题块或内联 `<script>` 逻辑。

### 5.2 脚本约定

- **所有网络请求必须经由 `js/api.js`**。页面 js 中不得直接出现 `fetch(`。
- 页面 js 的函数必须写成**全局函数声明**（`function foo() {}`）。**不得**包进立即执行函数，**不得**使用 `<script type="module">`——页面里保留了行内事件属性（`onclick`、`onsubmit`），模块作用域下这些函数不存在，按钮会集体失效。
- 卡片渲染必须复用 `js/common.js` 的 `renderCard`，**不得各页各写一份**。状态文案、配色映射、类型文案同理，全部来自 `common.js` 的共用常量。
- 网络失败时捕获异常并给出与页面现有风格一致的反馈，不允许让异常冒泡到控制台后页面停在空白状态。

### 5.3 DOM 与样式约定（这几条踩了就"静默失效"）

- 卡片必须按页面输出对应的 `data-*` 属性：**首页 `data-card`，搜索页 `data-result` 与 `data-keywords`**，两页都要 `data-id`。
- 首页卡片必须是 `#list` 的**直接子 `<a>`**。
- 以上两条不是风格问题：主题 CSS 用 `#list > a, #resultList [data-result]` 选中卡片，属性或结构丢了**不会报错**，只会让卡片变白、丢掉左侧金线。
- **不得改动主题文件里的选择器所依赖的 DOM 结构**（`#phone-canvas`、`#list`、`#resultList`、`#home-hero`、`#toast`、`#emptyState` 及其内部层级）。需要改结构时，同步改主题里的选择器，并在提交说明里写明。
- 主题通过**覆盖 Tailwind 类名**实现配色，HTML 里的类名与最终颜色不一致（写着 `bg-blue-600`，渲染是朱砂橙）。改配色请改主题里的 CSS 变量，不要按类名字面意思换类名。
- 动态生成样式类时，必须同步把该类加进对应页面的**隐藏"动态样式占位" div**，否则 Tailwind 运行时不会生成它。

### 5.4 安全与数据写入

- 写入 `innerHTML` 的**任何**来自接口或用户输入的内容必须转义（复用 `common.js` 的 `escapeHtml`）。能用 `textContent` 的地方优先用 `textContent`。
- 联系方式默认只展示后端返回的 `masked`；完整联系方式仅在用户点击后展示。
- 不得把完整联系方式写进日志、URL 参数或任何持久化存储。

### 5.5 文案与交互

- 校验逻辑、错误文案、提示文案、状态文案**属于需求**，必须与现状**逐字一致**。不得"顺手优化"措辞或"补全"校验规则（例如给手机号加正则）——那是需求变更，要走 PRD 变更流程。
- 不新增页面、不新增表单字段、不新增加载态 UI。

## 6. 数据与接口规范

- 服务端字段用 `snake_case`；返回给前端的 JSON 字段名以**现有前端渲染读取的名字为准**（如 `timeLabel`、`card_desc` 之类的取舍由 `serialize.py` 统一处理，不在前端做名字转换）。
- 枚举取值固定：`type ∈ {seek, find}`，`status ∈ {seeking, unclaimed, resolved}`。不得新增取值而不更新 PRD 与数据库约束。
- 时间统一为 `'YYYY-MM-DD HH:mm'` 字符串；跨层的相对时间文案（`今天 08:20`）只在服务端生成。
- 列表接口统一返回 `{count, items}`；`count` 必须与当前筛选条件下的真实条数一致。

## 7. 文档规范

### 7.1 各文档的职责边界

| 文档 | 什么时候必须改 |
| --- | --- |
| `docs/PRD.md` | 需求、验收标准、变更说明变化时（新增/调整某条 H/S/D/P/U 需求、改配色或文案的决策） |
| `docs/system-design.md` | 目录结构、数据库表、接口（路径/参数/响应字段/状态码）、关键流程、种子数据、迁移方案、测试清单变化时 |
| `docs/development-plan.md` | 阶段划分、任务顺序、工期、风险变化时 |
| `docs/coding-standards.md` | 本规范自身变化时 |

### 7.2 同步规则

- **同一次提交内完成**，不允许"代码先合，文档下个提交补"。
- 判断方法：如果这次改动会让**另一个人照文档做却做错**，那文档就必须改。
- "做了什么"由代码本身和文档承担；代码里要写的是"为什么这样做"，细则见 7.3。

### 7.3 注释规范

HTML 与代码都要有**适合的中文注释**，目的是让接手的人不看文档也能读懂这一块在做什么。

**语言**：注释用中文；标识符（变量、函数、类、CSS 类名）保持英文。

**一句话标准**：注释回答"这块是干什么的"和"为什么非得这么写"；不复述代码字面在做什么——那是代码自己的事。

#### 7.3.1 必须写注释的地方

| 位置 | 要求 |
| --- | --- |
| 每个源文件开头 | 说明本文件职责；JS 还要写明它属于哪个页面、依赖哪些共用文件 |
| 每个 HTML 页面顶部 | 这页是什么、依赖哪些脚本、数据来自哪个接口（尚未实现的要写明） |
| **每一个函数**（JS 与 Python，含内部辅助函数与校验器） | 上方必须有注释，写清"做什么、参数、返回值、约束"。**没有例外**——"这个函数太简单了"不是不写的理由 |
| 每个 Python 模块 | docstring；参数里有"由外部传入"这类约定的要写明原因 |
| 每个主要 HTML 区块前 | 标注用途，如 `<!-- 信息明细 -->` |
| **由脚本渲染的容器** | 必须标注**数据来源**，例如 `<!-- 列表由 js/index.js 请求 /api/items/home 后渲染；此处不得再写死数据 -->` |
| **看起来奇怪但必须这么写的地方** | 必须写明原因，否则后人会"顺手改掉"。典型：演示数据的 `masked` 不由 `contact` 推导；卡片必须带 `data-result`、必须是 `#list` 的直接子 `<a>`；页面 js 必须用全局函数声明（行内 `onclick` 依赖）；`time_display` 是固定文案、不按真实日期推导 |

#### 7.3.2 函数注释写什么

每个函数上方的注释至少回答四件事：

1. **做什么** —— 一句话说清职责，不要拿函数名换几个词复述一遍。
2. **参数** —— 每个参数的含义与取值范围。参数是"由外部传入"的（时间、数据库连接这类）要说明为什么，这样别人才不会把它挪进函数体里。
3. **返回什么** —— 返回值的形状；可能返回 `null` / `—` / 抛异常的情况要写明。
4. **约束与坑** —— 调用方必须注意的事：依赖哪个 DOM id、依赖哪条 CSS 选择器、不能改成什么、会在哪个阶段被替换掉。

格式：JS 用 `/** … */` 块注释，Python 用 docstring。很短（一两行）的函数可以压成一句话，但**"做什么"和"约束"两要素不能省**。

示例（Python）：

```python
def format_card_time(time_display, happened_at, now):
    """把一条物品的时间转成列表卡片上要显示的文案。

    参数：
        time_display: 固定展示文案（如「今天 08:20」）。非空时**原样返回**——
            演示数据的"今天"冻结在 2026-09-27，按真实日期重算会立刻变成 09-27。
        happened_at: 绝对时间 'YYYY-MM-DD HH:mm'，仅在 time_display 为空时使用。
        now: 当前时间。由调用方传入而不是在函数内取，单元测试才能固定时间。

    返回：
        卡片文案（'今天 HH:mm' / '昨天 HH:mm' / 'MM-DD HH:mm'）；
        时间串无法解析时原样返回；两者都为空时返回 '—'。
    """
```

示例（JS）：

```js
/**
 * 渲染一张列表卡片，返回 HTML 字符串。
 *
 * @param {Object} item    接口返回的列表项，读 id / name / type / status / icon / desc / time / place
 * @param {string} variant 'home' 输出 data-card；'search' 输出 data-result 与 data-keywords
 * @returns {string} 卡片 <a> 的完整 HTML
 *
 * 约束：variant 决定的那两个属性不是摆设——主题 CSS 用
 * `#list > a, #resultList [data-result]` 选中卡片，漏掉属性会让卡片静默丢掉
 * 左侧金线与圆角，且不会报错。所有来自接口的值都经 escapeHtml 转义后才写入 innerHTML。
 */
```

#### 7.3.3 不必写注释的地方

- 复述代码字面意思的注释：`// 设置名称`、`/* 遍历卡片 */`
- 纯装饰性的分隔线注释
- 把需求背景整段搬进代码——那属于 `docs/`

#### 7.3.4 HTML 注释的写法

HTML 注释不是元素，不参与弹性布局，也不影响 `#list > a`、`#resultList [data-result]` 这类子选择器，因此可以放心按区块标注。写法上：

- 区块用途放在该区块的开标签之前
- 动态容器写清"谁来填、填什么、不能改成什么"
- 一行讲完，不要跨多行排版

#### 7.3.5 维护要求

- **改行为时同步改注释**；注释与代码不一致按**缺陷**处理，不是"小问题"。
- **删代码要连注释一起删**。例如列表卡片被删掉后，`<!-- 校园卡 / 寻物 -->` 这类只标注旧数据的注释必须一并清理——留下无主的标签比没有注释更糟，因为读的人会以为那里还有一张卡片。
- 新增功能时先写注释再写实现，可以让"这块到底要干什么"先想清楚。

## 8. 提交规范

- **一个阶段一次提交**（对应开发计划的阶段 0–5），提交信息含阶段编号与内容概述，便于出问题时整体回退。
