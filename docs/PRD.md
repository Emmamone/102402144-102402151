## 2. 背景与目标

### 2.1 现状

现行版本是 5 个纯静态 HTML 页面（`home.html` / `search.html` / `detail.html` / `publish.html` / `success.html`），采用已定稿的「校园档案」视觉主题（墨绿 `#173f37` / 暖纸白 `#f6f3eb` / 朱砂橙 `#e86143`）。数据以三种方式硬编码在前端：

1. **列表数据写死在 HTML 里**：首页的 6 张卡片、搜索页的 8 张卡片都是静态 `<a>` 标签。
2. **详情页内嵌数据对象**：`detail.html` 里的 `ITEMS` 对象保存 8 条完整记录。
3. **`localStorage` 充当数据库**：
   - `campusNewItem`：发布的新信息（publish 写；success、detail 读；**并且 home 与 search 会据此在列表顶部临时插入一张卡片**）。
   - `campusResolved`：已解决的物品 id 数组（detail 写，home / search / detail 读）。

此外，整套主题样式被内联复制在 5 个页面里（每份约 127 行，字节完全相同），仓库中另有一份未被任何页面引用的 `visual-theme.css`。

由此带来的问题：

- 同一份数据在三个页面各存一份，且**已经不一致**——首页 1 号物品的描述比详情页的短一截。
- 数据没有持久化，换浏览器或清缓存即消失，**不同设备之间完全不共享**——原型本身只是本机演示，没有服务端存储、也没有账号与权限。本改造正是补齐这一环。
- 搜索只是对前端 `data-keywords` 字符串做子串匹配，没有真正的查询能力。
- 物品状态是**每个浏览器私有**的，同一件物品在不同人手机上状态不同。
- **新发布的信息只是本机可见**：靠列表页的脚本读 `localStorage` 临时插一张卡片，重启数据仍在但换设备就没了，也没有进入真正的信息列表。
- 主题样式在 5 个文件里重复维护，改一处配色要改五遍。

### 2.2 目标

在**页面外观与操作流程保持不变**的前提下，把数据存储、筛选、搜索、排序、状态变更全部搬到后端，前端只负责"发请求 + 渲染响应"，并为后续扩展（用户体系、图片、认领流程）打下一个可维护的基础。

### 2.3 非目标（本期明确不做）

- 不做图片/附件上传（现有页面完全没有上传 UI 与图片字段，新增会改变页面结构）。
- 不新增表单字段、不新增页面。
- **不改动视觉主题**：现行版本的「校园档案」主题即为"页面不变"的新基线——配色、字体、卡片样式、图标、文案一律不动。（主题样式会从 5 份内联副本抽成 1 份共用文件，属于代码整理，不改变渲染结果。）
- 不做用户注册登录与权限体系。
- 不做分页与无限滚动（当前数据量小，且分页会引入新的页面控件）。
- 不改动 `modao.cc` CDN 提供的 Tailwind JIT 与 Iconify 图标方案（主题样式虽会外置，但仍依赖该 CDN 提供 Tailwind 基础类）。

## 3. 用户角色与使用场景

本期只有一类角色：**访客（学生）**，无需登录。同一角色可以完成全部操作。

| 场景 | 描述 |
| --- | --- |
| 快速浏览 | 打开首页，看最新发布的失物/招领信息，按「全部 / 寻物 / 招领」切换。 |
| 定向查找 | 在首页搜索框输入关键词（如"校园卡"）进入搜索结果页，可再按类型筛选。 |
| 查看详情 | 从列表进入详情页，核对时间、地点、描述；点击"联系发布者"查看完整联系方式。 |
| 发布信息 | 在发布页选择"我要寻物 / 我要招领"，填写 6 项必填信息后提交。 |
| 标记已解决 | 物品找回或归还后，在详情页点击"标记为已找回 / 标记为已归还"，状态变为"已解决"。 |

## 4. 需求范围

### 4.1 本期范围

1. 前后端分离：数据与业务逻辑全部下沉到后端，前端只发请求与渲染。
2. 数据持久化：8 条演示数据 + 用户新发布的数据统一存入 SQLite。
3. 全部页面的读路径改为调用后端接口。
4. 发布与标记已解决两个写路径改为调用后端接口。
5. 新发布的信息**真实出现在**首页「最新信息」与搜索结果中，且**对所有设备可见、可持久保存、可被搜索**（不再依赖本机的临时插入）。
6. 页面 HTML / CSS / JS 分离：每个页面一个独立 `.html`，一套共用的主题样式文件，每页一个独立 `.js`；HTML 内不再有内联 `<style>` 与内联脚本逻辑。
7. 首页文件更名为 `index.html`，作为站点入口（`/` 直接可访问）。
8. 交付《产品需求文档》《系统设计文档》《开发计划》《代码规范》四份中文文档。

### 4.2 明确排除项

| 排除项 | 原因 |
| --- | --- |
| 图片/附件上传 | 现有页面没有上传 UI 与图片字段，新增会改变页面结构，违背"页面不变"。 |
| 新增表单字段（如学号、手机号校验规则） | 同上。 |
| 用户登录与实名 | 本期无账号体系，范围为演示级。 |
| 分页 | 数据量小，且分页控件属于新增 UI。 |
| 修改视觉样式与布局 | 本期的约束就是外观不变。 |

## 5. 页面与功能需求

### 5.1 首页（`index.html`，原 `home.html`）

**页面结构**：顶部标题与搜索框 → 分类标签栏（全部 / 寻物 / 招领）→ 「最新信息」列表 → 底部「发布信息」按钮。

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| H-1 | 打开首页默认展示「最新信息」列表 | 首次进入显示全部未筛选信息。 |
| H-2 | 列表计数 | 显示"共 N 条 · 按发布时间排序"，N 为当前筛选条件下的**真实条数**。 |
| H-3 | 分类切换 | 点击「全部 / 寻物 / 招领」重新请求并渲染列表，标签样式同步高亮。 |
| H-4 | 卡片内容 | 每张卡片展示：类型图标、物品名称、类型标签（寻物/招领）、状态标签（寻找中/待认领/已解决）、时间、地点、两行描述。点击进入详情页。 |
| H-5 | 已解决卡片弱化 | 状态为「已解决」的卡片整体降低不透明度（沿用现有 `opacity-80` 效果）。 |
| H-6 | 搜索入口 | 搜索框为空时点击提交，弹出提示"请输入物品名称或关键词"；非空时跳转搜索结果页并带上关键词。 |
| H-7 | 发布入口 | 底部按钮跳转发布页。 |
| H-8 | 新发布信息置顶 | 用户新发布的信息出现在列表**最前面**。现行版本只是在本机从 `localStorage` 临时插一张卡片（`insertLocalPost`，换设备即失效）；改造后由后端返回并置顶，**全局可见、可搜索、可持久保存**（见第 9 节 C-3）。 |
| H-9 | 不保留本机临时插入 | 移除靠 `localStorage` 往列表顶部插卡片的逻辑，列表内容**唯一来源是后端返回的数据**，避免同一件物品出现两张卡片。 |

### 5.2 搜索结果页（`search.html`）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| S-1 | 关键词匹配 | 对物品的**搜索索引文本**做不区分大小写的子串匹配。索引文本包含物品名称、类别、地点、描述以及类型同义词（如"寻物 丢了""招领 捡到"），因此搜"蓝色卡套""3号楼"这类描述外的词也能命中。 |

| S-7 | 默认关键词 | 不带参数进入时，搜索框预填"校园卡"（沿用现有默认值），因此首屏默认展示 2 条结果（1 号、7 号）。 |
| S-8 | 结果顺序 | 保持现有展示顺序：1、7、5、3、2、4、6、8；新发布的信息排在结果最前。 |
| S-9 | 提交才搜索 | 仅在用户提交表单或点击快捷标签时触发搜索，不做输入即时搜索（避免改变现有交互）。 |
| S-10 | 不保留本机临时插入 | 与首页同理，移除靠 `localStorage` 往结果顶部插卡片的逻辑，结果**唯一来源是后端**。 |

## 6. 数据与状态规则

### 6.1 物品类型（type）

| 值 | 中文 | 含义 | 初始状态 |
| --- | --- | --- | --- |
| `seek` | 寻物 | 我丢了东西，寻找 | `seeking` 寻找中 |
| `find` | 招领 | 我捡到东西，等人认领 | `unclaimed` 待认领 |

### 6.2 物品状态（status）

| 值 | 中文 | 标签配色 |
| --- | --- | --- |
| `seeking` | 寻找中 | 橙色 |
| `unclaimed` | 待认领 | 琥珀色 |
| `resolved` | 已解决 | 绿色（卡片同时降低不透明度） |

状态流转：`seeking` / `unclaimed` → `resolved`，**不可逆**（本期不提供撤销）。

### 6.3 展示顺序

| 场景 | 规则 |
| --- | --- |
| 首页「最新信息」 | 用户新发布的信息在前（按发布时间倒序），其后是演示数据，按固定顺序 1~6 排列。 |
| 搜索结果 | 用户新发布的信息在前，其后是演示数据，按固定顺序 1、7、5、3、2、4、6、8 排列。 |

两个顺序都是**固定顺序**而非发布时间排序——现有页面就是这样展示的，本期不改变。

### 6.4 物品编号

- 演示数据：`LF-001` ~ `LF-008`。
- 用户新发布：按真实自增 id 生成，如第 9 条为 `LF-009`。
- 变化说明：旧版新发布物品的编号固定显示为 `LF-NEW`，本期改为真实编号（因为它已经是可被搜索到的正式数据）。

### 6.5 联系方式脱敏规则

| 输入形态 | 展示 |
| --- | --- |
| 11 位手机号（`1` 开头） | 前 3 位 + `****` + 后 4 位，如 `138****6621` |
| 其它长度大于 4 的字符串 | 前 2 位 + `****` + 后 2 位 |
| 长度不超过 4 | 原样显示 |
| 空 | `—` |

> 注意：演示数据的脱敏串是**独立固定的展示值**，不一定由联系方式推导而来（例如 1 号物品的联系方式是微信号，脱敏串却是手机号形态）。因此演示数据的脱敏串按原值保存；只有用户新发布的数据才按上表规则计算。

## 7. 接口需求（概述）

完整定义见《系统设计文档》第 5 节。本章只列能力要求：

| 能力 | 要求 |
| --- | --- |
| 首页列表 | 支持按类型筛选，返回条数与列表数据，顺序按 6.3。 |
| 搜索 | 支持关键词子串匹配 + 类型筛选，返回条数与列表数据，顺序按 6.3。 |
| 详情 | 按 id 返回完整字段，含脱敏联系方式与完整联系方式。 |
| 发布 | 接收 6 个表单字段，在后端补全状态、图标、编号、脱敏串、发布时间、搜索索引后落库，返回新记录。 |
| 标记已解决 | 按 id 把状态置为已解决，返回更新后的记录。 |

数据校验要求：后端对表单字段做二次校验（类型取值、类别取值、字符串非空、时间格式），作为前端校验之外的兜底。

## 8. 非功能需求

### 8.1 代码组织

| 要求 | 说明 |
| --- | --- |
| 一页一 HTML | 5 个页面各自独立，不使用单页应用，不做页面合并。 |
| 一页一 JS | 每个页面的业务逻辑存放在与该页同名的独立 js 文件中（`index.js` / `search.js` / `detail.js` / `publish.js` / `success.js`）。 |
| 无内联脚本 | HTML 中不再保留任何内联 `<script>` 逻辑代码块，只保留对外部 js 的引用。 |
| 无内联样式 | HTML 中不再保留内联 `<style>` 主题块，改为引用**一份**共用的主题样式文件（现行版本同一套主题被复制在 5 个文件里，改一处要改五遍）。 |
| 共用代码独立 | 主题样式、请求封装与跨页共用的展示工具单独成文件，不重复实现。 |
| 页面可直接访问 | 5 个页面各自都能通过 URL 直接打开（不依赖先经过其它页面）。 |

### 8.2 性能

- 本地环境下接口响应应为毫秒级，页面首屏不引入明显等待。
- 不引入骨架屏等新的加载态 UI（会改变页面结构），仅在容器初始为空到数据渲染完成之间有极短暂的空窗。

### 8.3 兼容性

- 面向移动端视口（现有页面为 393×852 的移动框架）。
- 依赖浏览器 `fetch`，面向现代浏览器。

### 8.4 外部依赖

- 页面仍从 `modao.cc` CDN 加载 Tailwind 运行时与 Iconify 图标组件，**离线环境不可用**。
- 页面必须通过 http 访问，直接双击 HTML 文件（`file://`）会因跨域限制导致接口请求失败。

### 8.5 工程质量（代码规范与测试）

本项目要求"代码、测试、文档"同步产出，细则见《代码规范》`docs/coding-standards.md`。需求层面的约束：

| 编号 | 要求 |
| --- | --- |
| Q-1 | 编写代码时**同步编写单元测试与集成测试**，不允许"先写代码、测试回头补"。 |
| Q-2 | 测试统一放在仓库根目录的**测试层** `tests/` 下，分层为 `unit/`（纯函数与校验规则）、`integration/`（接口端到端）、`contract/`（接口字段与前端渲染的契约）。测试文件不得散落在 `backend/` 里。 |
| Q-3 | 集成测试必须使用**临时数据库**，不得读写仓库中的演示数据库文件。 |
| Q-4 | 每项任务"完成"的定义包含：功能实现、对应自动化测试已通过、`pytest -q` 全绿、受影响文档已在同一次提交内更新。 |
| Q-5 | 代码变更影响**需求 / 接口 / 目录结构 / 开发顺序**时，必须同步更新对应文档（PRD / 系统设计 / 开发计划）。 |
| Q-6 | 前端不引入 Node 构建与测试环境；前端所依赖的接口字段由 `contract` 层测试保证，页面本身的端到端行为由系统设计文档第 12 节的手工验收清单覆盖。 |
| Q-7 | **持续集成与测试层绑定**：任何分支的 push、任何 PR 都自动运行代码风格检查与三层测试，任一层失败即构建失败。 |
| Q-8 | 三个测试层各自独立成步，构建失败时能直接定位到是哪一层，不必翻日志。 |
| Q-9 | 测试层缺失时必须**显式失败**，不允许出现"没有测试却显示通过"的假绿。 |
